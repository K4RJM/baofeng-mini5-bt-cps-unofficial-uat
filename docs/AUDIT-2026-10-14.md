## Scope, method and limits

This is a source-based engineering audit, with adversarial, in-memory probes. It is not hardware certification or an external laboratory assessment. The same assistant that contributed to development performed this review; the findings below are supported by code and reproducible observations rather than an assertion of organizational independence.

All 42 files in the reviewed repository tree matched the local audit copy by Git blob SHA-1. Application modules, configuration/schema tables, tests, deployment workflow, packaging, local server and documentation were inspected. The 11 protected-core hashes passed their existing checks.

No application source, tests, configuration, dependencies, UI, protocol, memory map or firmware was changed during the audit. The audit session itself did not connect, read or write a physical radio. Additional probes used synthetic data and simulated transports. No factory CPS application was run. No package installation was needed. The only subsequently authorized repository change is publication of this report.

Code links below are pinned to the audited application commit. Line references identify that version, even after future corrections.

## A. Executive Summary

The application has a useful experimental foundation: a small dependency-free runtime, a passive native-DAT parser, isolated pure channel-operation helpers, explicit programming confirmation, a fixed write-address sequence, one-use write permits, conservative handling of ambiguous writes, and an explicit distinction between acknowledged transfer and verified storage.

However, the radio-data conversion is not reliable across the application's own advertised option domain. Several valid settings change during decoding, and VFO DTMF group values overlap direction bits. These are confirmed software defects, not disagreements over style or AI-assisted development. They can affect a read-edit-write cycle even if the intended edit concerns a different channel.

The full writer also reconstructs bytes that are not represented in DAT rather than preserving a complete source image. This is disclosed in safety documentation, but the consequences for noncanonical device contents and other firmware variants remain unverified. The new immediate post-write disconnect is an explicitly experimental lifecycle change: the code proves that acknowledgements were received, not that firmware has completed an internal durable save.

The existing 41 tests are valuable but insufficient. They pass while the additional option-domain checks reproduce 29 mismatches. The synthetic read/write oracle is largely generated by the same encoder under test, and the Bluetooth simulator does not model real connection setup, firmware commit or reboot.

**Assessment:** suitable for continued controlled development and offline DAT editing, with material radio-programming integrity risks. I would not certify the current Bluetooth writer for unrestricted use, expand to more radios, or add substantial programming features before resolving the confirmed conversion defects and establishing a controlled hardware validation baseline.

**Findings:** no confirmed Critical arbitrary-address-write or executable-deserialization exploit was found; 6 High, 7 Medium and 2 Low findings follow. High findings include both confirmed defects and explicitly identified hardware-dependent risks. Severity is a prioritization judgment, not a claim that hardware damage has been demonstrated.

Nothing in this audit establishes the cause of the earlier inoperable radio or the intermittent PC Bluetooth-reset symptom.

## B. Critical and High-Risk Findings

### F01 — Full reconstruction does not preserve unmapped bytes from a radio read

**Severity:** High.  
**Status:** byte changes reproduced; their physical consequences are unverified.

**Locations:** [radio-encoder.mjs:25–31, 45–55](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-encoder.mjs#L25-L55), [writer.mjs:25–39](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/writer.mjs#L25-L39), [app.mjs:191–195](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L191-L195).

**Problem and source evidence:** `offlineFrames()` creates a 33,344-byte image initialized to FF, and settings blocks are rebuilt from selected fields. `makePlan()` uses that reconstruction. Although a radio read retains `backup.raw`, the UI does not merge edits into that capture when constructing a write. DAT cannot represent all captured bytes.

**Example/reproduction:** starting with a synthetic valid plan, changing decoded byte 0x7D00 to 0x12 and an unmapped general-settings byte at address 0x9013 to 0x34, then decoding and rebuilding, changed them to FF and 00 respectively. The intervening DAT round trip preserved its configuration object semantically; the loss occurred outside that object model.

This is not evidence of an out-of-approved-range write. It is evidence that approved-range contents can change outside the edited fields. Some normalization may match factory CPS behavior, but that must be established for each affected region and variant rather than assumed.

**Recommended correction:** define which bytes are mapped, deliberately normalized, required constants or genuinely unknown. Preserve a validated source capture or block unsupported noncanonical contents according to an approved per-device policy. Retain an original raw diagnostic capture separately from a derived DAT. Do not blindly copy or overwrite unknown bytes without validation. A preservation change can still produce the existing complete 262-block write; it does not require partial writing.

**Suggested regression test:** use independent, anonymized raw captures containing nondefault reserved bytes. Edit one field and compare every source/destination byte against an explicit change allowlist, including the three padded region ends.

### F02 — Decoder modulo operations silently change valid supported settings

**Severity:** High.  
**Status:** confirmed and reproduced using accepted configuration values.

**Locations:** [radio-decoder.mjs:4, 15, 22–27](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-decoder.mjs#L4-L27), [radio-encoder.mjs:25–43](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-encoder.mjs#L25-L43), [tests/core.test.mjs:18](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/tests/core.test.mjs#L18).

**Problem and source evidence:** the decoder uses modulo as normalization. For example, PTT delay is reduced modulo 7, VFO PTT identification modulo 3, and VFO squelch signaling modulo 2. Those bounds do not match the option values accepted by the writer and offered by the editor. Unknown raw values can also become plausible valid values rather than being rejected or preserved.

**Example/reproduction:** accepted PTT-delay code 28 decoded as 0; VFO PTT-identification code 3 decoded as 0; both VFO squelch-mode codes 2 decoded as 0. A configuration containing the last three values produced three changed raw bytes after decode/rebuild. The complete single-option sweep found 29 mismatches, including 22 PTT-delay cases; four additional mismatches in that count belong to F03.

A realistic trigger is reading a radio configured with one of these settings, changing a channel name, and writing the full configuration. The initial read has already changed the displayed/saved setting.

**Recommended correction:** verify the native representation against independent factory CPS/capture evidence, make encoder/decoder domains agree, and preserve or explicitly reject unrecognized values instead of coercing them into valid-looking defaults.

**Suggested regression test:** round-trip every accepted enum value, then representative combinations. Compare configuration fields and independently expected raw bytes. Include unknown raw codes and verify that none silently becomes a different supported setting.

### F03 — VFO DTMF group packing overlaps the offset-direction field

**Severity:** High.  
**Status:** confirmed internal encoding/decoding inconsistency; exact firmware interpretation requires hardware/native-CPS validation.

**Locations:** [radio-encoder.mjs:35–43](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-encoder.mjs#L35-L43), [radio-decoder.mjs:13–16](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-decoder.mjs#L13-L16).

**Problem and source evidence:** VFO byte 14 is encoded as `(direction << 4) | signalGroup`, although accepted signal-group codes span 0–19. Codes 16–19 occupy a direction bit. The A decoder also takes the entire byte as the signal group, while B masks it to four bits.

**Example/reproduction:** with direction Off and group code 16 (displayed group 17), A decoded with direction Plus. B decoded as Plus with group code 0. A configured with direction Minus and group code 0 decoded with group code 32; rebuilding then failed with `Unrecognized CPS value: vfoASignalGroup`.

This can misrepresent a repeater VFO or prevent a read-edit-write operation. It creates a plausible wrong-transmit-frequency risk if the direction interpretation matches the radio, but that physical outcome was not tested.

**Recommended correction:** establish the actual bit layout and supported group domain from native CPS and approved hardware observations. Until verified, block ambiguous combinations rather than guessing a replacement shift/mask.

**Suggested regression test:** check all supported direction × group combinations for both VFOs, asserting that changing one never changes the other. Include all twenty displayed groups and native byte fixtures independent of this encoder.

### F04 — Small malformed DAT graphs can expand far beyond the parser's input limits

**Severity:** High.  
**Status:** bounded amplification reproduced; tab exhaustion/crash at larger sizes is a plausible, deliberately untested consequence.

**Locations:** [dat.mjs:5–29](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/dat.mjs#L5-L29), [app.mjs:121, 198](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L121), [channel-import-ui.mjs:32–36](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/channel-import-ui.mjs#L32-L36).

**Problem and source evidence:** `resolve()` recursively expands every reference without memoization or a total expansion budget, before final structural validation. The two-megabyte input limit, 50,000-record limit and depth limit do not bound the number of expanded objects. Both file-open paths also read the complete file into memory before the parser checks its size.

**Example/reproduction:** a 243-byte, two-level shared-array graph represented 400 logical string occurrences. A 461-byte, four-level graph represented 160,000 occurrences before rejection. Further levels can grow multiplicatively while remaining below the existing depth and serialized-record limits. Opening an untrusted DAT could freeze the tab and lose unsaved work; no code execution is necessary.

**Recommended correction:** check `File.size` before reading, validate expected graph shapes early, reject cycles, and apply explicit limits to total resolved nodes/string bytes/array entries. Use an appropriate memoized graph-resolution strategy without allowing alias expansion to evade those limits.

**Suggested regression test:** exercise shared-reference graphs, cycles, deep nesting, duplicate object IDs, huge declared arrays and oversized files under strict time/memory budgets. Verify rejection before workspace replacement.

### F05 — Model matching and DAT loading do not establish device compatibility or source provenance

**Severity:** High.  
**Status:** confirmed limitation; starter-DAT trust conversion reproduced. Damage to another variant is an unverified risk.

**Locations:** [read-test/reader.mjs:62–70](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/read-test/reader.mjs#L62-L70), [writer.mjs:18–19, 69–79](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/writer.mjs#L18-L79), [app.mjs:67, 75, 193–198](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L67-L198), [index.html:24](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/index.html#L24).

**Problem and source evidence:** identification checks the string `5RMINI`, not a verified firmware/hardware profile. `load()` marks every structurally accepted DAT as trusted. Backup protection is an explicit checkbox attestation; the writer neither checks a backup artifact nor validates its compatibility. These are real safeguards against casual mistakes, but not proof of a safe codeplug.

**Example/reproduction:** the initial starter workspace had writing disabled. Exporting it to DAT and reopening that same generated file enabled Write radio, with zero simulated radio connections. A different firmware variant returning the same model string would also pass the executable identity gate. The warning accurately discloses this limitation, but does not enforce compatibility.

This is not an automatic write or a bypass of the actual confirmation checkbox: explicit write consent is still required. It demonstrates that `trustedBase` means loaded file/read, not independently validated device provenance.

**Recommended correction:** define approved device/profile and source-provenance policy, distinguish parsed from hardware-validated configurations, and fail closed on unsupported combinations. If firmware cannot be identified using existing approved information, do not claim that it can; use an explicit compatibility workflow or restrict support until verified. Clarify exactly what the backup attestation guarantees.

**Suggested regression test:** test same-model/different-profile devices, cross-device source data, incompatible DAT variants, and exported starter DAT reimport. Verify that the intended policy survives export/import and source switching. Hardware validation remains necessary.

### F06 — Immediate post-ACK disconnect lacks evidence about durable commit and reboot timing

**Severity:** High.  
**Status:** implementation confirmed; harmful hardware behavior is unverified, not a demonstrated defect.

**Locations:** [connection-recovery.mjs:2–12](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/connection-recovery.mjs#L2-L12), [app.mjs:195](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L195), [tests/simulate.mjs:4–12](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/tests/simulate.mjs#L4-L12), [docs/SAFETY.md:21](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/docs/SAFETY.md#L21).

**Problem and source evidence:** cleanup requests a browser GATT disconnect immediately after the final acknowledgement and after the writer becomes idle. That proves the transfer's acknowledged state, not completion of internal flash/NVRAM work. The simulator updates memory before ACK and cannot represent delayed firmware commit or reboot interactions.

**Example:** on a firmware variant that finishes an internal save after acknowledging the final block, immediate link teardown could interact with that process. Conversely, explicit host teardown may correctly solve a stale-link problem. This audit cannot choose between those outcomes from software simulation.

The cleanup sends no extra programming/reset opcode, and the read-back prompt correctly waits for operator readiness rather than a five-second assumption. Those are positive properties, but do not validate hardware timing.

**Recommended correction:** keep this classified as experimental until a documented test plan establishes safe ordering, persistence after reboot/power cycle, and repeated reconnect behavior on the supported radio/PC/browser combination. Do not infer a safe delay or invent a reset opcode without evidence.

**Suggested regression test:** add simulations of ACK followed by delayed disconnect, reboot during final ACK delivery, incomplete commit and host cleanup failure. Separately perform authorized physical persistence/reconnect tests; simulation alone cannot close this finding.

## C. Medium and Low-Risk Findings

### F07 — Accepted frequency representation and radio decoder disagree

**Severity:** Medium. **Status:** reproduced in software; frequencies outside actual hardware capability are not endorsed.

**Locations:** [validation.mjs:7, 18](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/validation.mjs#L7-L18), [radio-encoder.mjs:10–13](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-encoder.mjs#L10-L13), [radio-decoder.mjs:8–10](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-decoder.mjs#L8-L10).

**Problem/evidence:** editing accepts the three-digit 100–999 MHz representation; encoding accepts canonical three-digit strings; channel decoding returns blank for values at or above 600 MHz. Invalid BCD nibbles are not explicitly rejected.

**Example:** a synthetic accepted 650.00000 MHz configuration decoded as an empty RX channel. This demonstrates an internal domain mismatch, not that this radio supports 650 MHz.

**Correction:** use verified per-model receive/transmit capabilities consistently. Distinguish an unsupported or malformed record from an actually empty slot instead of silently converting it to empty.

**Regression test:** cover representational and approved hardware boundaries, invalid BCD, blank TX and receive-only cases, asserting explicit rejection or preservation.

### F08 — The interface's 999-channel capacity exceeds the writer's accepted capacity

**Severity:** Medium. **Status:** confirmed and reproduced; current behavior blocks rather than silently overwrites.

**Locations:** [channels.mjs:1–7](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/channels.mjs#L1-L7), [app.mjs:106–116](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L106-L116), [radio-encoder.mjs:51–54](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-encoder.mjs#L51-L54).

**Problem/evidence:** the editor exposes slot 999, but the encoder requires bytes 0x7CC0–0x7CFF—the final pair of records, including slot 999—to remain FF.

**Example:** putting a valid channel in index 998 exported successfully to DAT, but `makePlan()` rejected it with the last-channel-pair error. A populated extra record also blocks planning.

**Correction:** expose the currently verified write limit before edits/import placement, or resolve the last-record mapping under explicit approval and hardware validation. Do not remove the guard just to make the UI promise true.

**Regression test:** exercise slots 998, 999 and reserved 1000 across edit, move, append, DAT export and write planning; check early, accurate feedback.

### F09 — Channel Undo can revert later radio-wide edits

**Severity:** Medium. **Status:** reproduced; the expandable guide already warns about snapshot scope.

**Locations:** [app.mjs:58–61, 98, 107](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L58-L107).

**Problem/evidence:** channel operations snapshot the entire configuration. Optional/VFO/DTMF edits do not enter the same history, but Undo replaces the entire configuration with a previous snapshot.

**Example:** edit a channel name, change squelch code 3 to 4 in Optional settings, save, return to Channels and choose Undo. The channel name reverted as expected, but squelch also reverted to 3. No radio operation was involved.

**Correction:** use operation-scoped changes or a coherent whole-workspace history with clear action descriptions. At minimum, require an explicit decision before rolling back unrelated later settings. Documentation alone does not prevent an overlooked rollback before a full write.

**Regression test:** interleave channel, VFO, optional and DTMF edits, Save and Undo; assert the intended undo scope for each.

### F10 — Browser GATT promises have no application-level completion deadline

**Severity:** Medium. **Status:** missing deadline confirmed; a stall reproduced with a simulated never-resolving browser write promise.

**Locations:** [read-test/reader.mjs:27–31, 52–61](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/read-test/reader.mjs#L27-L61), [writer.mjs:57–59](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/writer.mjs#L57-L59), [app.mjs:63–72, 175, 204](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L63-L204).

**Problem/evidence:** the response timer is installed only after awaiting the native send promise. Native connect, discovery and notification setup are likewise awaited without a local deadline. A nonsettling browser call can leave the app busy indefinitely; idle handling is suspended while busy.

**Example:** after one simulated write emitted an ACK, its native-send promise was held pending. The operation remained busy past the simulator's normal response timeout, with `waiter` absent and the ACK buffered.

**Correction:** design operation-level deadlines and cancellation that mark a memory write uncertain and never retry it. A timeout must invalidate the operation generation so late native completion cannot resume an abandoned transaction.

**Regression test:** hold each native GATT promise pending; test late resolve/reject after cancellation, UI recovery and absence of subsequent write frames.

### F11 — Diagnostic evidence can be stale or lost when decoding fails

**Severity:** Medium. **Status:** confirmed by source trace; not separately reproduced in a browser.

**Locations:** [app.mjs:75, 170, 189–192](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L75-L192), [writer.mjs:62–67](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/writer.mjs#L62-L67), [radio-decoder.mjs:5–6](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/radio-decoder.mjs#L5-L6).

**Problem/evidence:** the latest raw capture is stored as `backup` only after decode and DAT serialization succeed. A fatal GBK decoding error can therefore discard a completed capture from the diagnostic path. Loading a different source also does not reset or rebind `radio.report`, and reads do not initialize their own report.

**Example:** a complete read containing an invalid name byte fails before `load(next,...,capture)`. The report can contain no capture—or a previous one—while `source` or transport stage refers to another operation. A disconnect after a previous acknowledged write can be logged as an expected reboot even during a later unrelated read.

**Correction:** retain operation-tagged raw captures before interpretation; distinguish current, prior and failed-operation evidence. Bind reports, plans, sources and device identity to a transaction ID, and redact/export them deliberately.

**Regression test:** inject a full capture that fails name decoding, then inspect the diagnostic export; also switch source after a write and fail a later read. Evidence and stage must remain correctly associated.

### F12 — Dirty-state tracking does not cover staged edits or confirmed file persistence

**Severity:** Medium. **Status:** reproduced with the real handlers in a synthetic DOM; actual OS download cancellation was not exercised.

**Locations:** [app.mjs:76, 125–160, 199, 209–212](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/app.mjs#L76-L212).

**Problem/evidence:** edits in the open channel dialog deliberately do not set `dirty`, and the unload guard checks only `dirty || busy`. Saving clears `dirty` immediately after requesting an anchor download, without evidence that a file was actually kept.

**Examples:** changing a staged channel name in an otherwise clean workspace did not trigger the unload guard. In a harness where the download click saved nothing, Save still cleared dirty state. Closing an editor as Cancel is intentionally different from accidentally closing the entire browser tab.

**Correction:** track pending dialog edits separately, and describe downloads as requested rather than confirmed durable saves unless a suitable completion mechanism is available. Preserve a clear indication of uncommitted work without treating ordinary Cancel as an error.

**Regression test:** close/reload with a changed editor open, with no-op edits, and after canceled/blocked downloads; check prompts and status semantics.

### F13 — Existing test oracles and DOM/transport fakes miss important behavior

**Severity:** Medium. **Status:** confirmed coverage limitation demonstrated by passing tests alongside reproduced defects.

**Locations:** [tests/core.test.mjs:18](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/tests/core.test.mjs#L18), [tests/fixtures.mjs:5–6](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/tests/fixtures.mjs#L5-L6), [tests/simulate.mjs:1–14](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/tests/simulate.mjs#L1-L14), [tests/interface.test.mjs:9–26](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/tests/interface.test.mjs#L9-L26).

**Problem/evidence:** the main radio fixture is produced by the same encoder whose correctness is being checked. The simulator bypasses actual connection discovery and delivers responses during the native write call. The DOM fake auto-creates missing IDs and does not enforce real constraints, inertness, modal behavior or event bubbling.

**Example:** all 41 tests passed while the independent option sweep found 29 mismatches. A missing HTML control can still appear in the fake DOM, and the fake cannot validate the Windows reconnect behavior that motivated v20.9.

**Correction:** retain the useful unit tests, but add independent native-CPS golden vectors, parameterized option/cross-field coverage, an event-faithful transport fake and targeted real-browser tests with radio APIs stubbed. Keep authorized hardware tests separate.

**Regression test:** demonstrate that deliberately wrong enum bounds, overlapping VFO bits, missing HTML IDs and an inertness violation each fail an appropriate test.

### F14 — Most dialogs lack explicit accessible names

**Severity:** Low. **Status:** missing labeling confirmed in markup; screen-reader behavior was not physically tested.

**Locations:** [index.html:11, 22–27](https://github.com/K4RJM/baofeng-mini5-bt-cps-unofficial/blob/14cfb85498b682545f221e4345503739d70ae3e9/index.html#L11-L27).

**Correction:** consistently label dialog containers and associate important warnings/descriptions. Preserve native keyboard focus and Escape handling.

**Regression test:** inspect the accessible tree for each dialog name and description; verify focus entry/return and keyboard-only confirmation/cancellation in a real browser.

### Native DAT integrity conclusion

For accepted, recognized schemas, an unchanged DAT object's fields—including unknown option codes, Chinese names, NUL suffixes and the extra 1,000th record—can survive export/import semantically. The serializer allocates fresh object IDs and a canonical record structure. An alternative valid object-ID serialization was loaded with equivalent values but saved with different bytes. **Byte-for-byte original-file preservation is not provided.**

A DAT derived from a radio read is different: decoder normalization and unmapped-byte loss occur before or outside the DAT model. A derived “original-read DAT backup” must not be mistaken for an exact raw capture.

Appending a second DAT preserves current Optional settings, VFOs, DTMF and the extra record. Opening a second DAT through Open CPS DAT intentionally replaces the complete workspace, with the current dirty-state caveats.

Structural compatibility was exercised through this parser/serializer and the existing schema. Current factory CPS acceptance of the exported files was not independently established during this audit.

### Concurrency and failure-state conclusion

The app busy guard and Writer busy guard prevent ordinary overlapping operations; visible editing controls are disabled/inert during programming. A new write locks its source before connection/upload. Canceling the write warning performs no radio write. Closing the tab still cannot be made physically safe by a browser unload prompt alone.

The writer stops after ambiguous send/ACK failures and does not resume automatically. Connection setup retries are separate from memory-write retries. These are important strengths. Native-promise stalls, weak transaction-associated diagnostics and hardware-dependent reboot timing remain unresolved.

## F. Architecture Recommendations

A wholesale rewrite or framework migration is not justified by this audit. Preserve the working pure channel helpers and the fixed transaction safeguards. Improve the boundaries that currently allow inconsistent representations and state.

1. **Make the radio profile authoritative.** Define approved identity/capability policy, channel limits, fields, encodings, enum domains, reserved-byte treatment and clone regions together. Encoder, decoder, validation and UI must agree with the same verified profile. Do not guess new firmware identifiers or commands.

2. **Separate transport from clone protocol and configuration conversion.** The current Reader/Writer inheritance mixes Web Bluetooth setup, byte buffering, command allowlisting and protocol sequencing. A future split should preserve the existing frame snapshot, address validation and no-retry contract. WebSerial would be a distinct transport implementation; cable protocol behavior must be independently validated.

3. **Keep raw capture and editable configuration as separate first-class objects.** A decoded DAT-compatible object is not a complete memory image. Preserve provenance and define explicit merge/normalization rules for any generated full write.

4. **Introduce a transaction coordinator.** Centralize operation state, device identity, source version, write plan, verification result, cancellation generation and diagnostic evidence. Replace fragile combinations of global flags only after tests capture current behavior. The goal is auditable invariants, not an abstraction for its own sake.

5. **Use one validated workspace-operation boundary.** Bulk edit, Copy/Paste/Duplicate, advanced sort and CSV import should produce proposed channel changes, validate them, preview collisions/capacity, then commit atomically. They should not call radio transport. Preserve the existing full-write policy unless separately approved.

6. **Make history scope explicit.** Use per-operation deltas or a coherent global history so a channel command cannot silently revert later unrelated settings.

7. **Move long UI/help assembly out of the transaction module gradually.** app.mjs combines file handling, channel operations, settings forms, tutorials, radio workflow, diagnostics and application state. Its compressed, long-line handlers make dependencies harder to review. Extract based on tested responsibility boundaries, not line count or formatting preference.

8. **Treat new radio models as independent drivers.** BF-F8HP and BF-F8HP PRO must not inherit MINI-5 memory/identity assumptions merely because they share a brand or similar name. Each needs verified file/transport/protocol/capability rules, negative cross-model tests and separate hardware evidence.

9. **Keep geographic organization above the driver layer.** Geographic metadata, optional external-data imports and future CSV interchange should never imply different radio memory semantics or silently replace native settings. RepeaterBook remains disabled pending approval; this audit performed no API calls to it.

No architecture recommendation is authorization to modify protected files. Changes must be staged behind independent fixtures and approved hardware-validation plans.
