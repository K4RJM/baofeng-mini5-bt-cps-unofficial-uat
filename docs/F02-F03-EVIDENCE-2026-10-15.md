October 16, 2026; v20.16. K4RJM explicitly accepted this disposition in the master task after completed physical testing. **The encoder and decoder are unchanged. No more physical F03 testing is requested.**

Bluetooth CPS observes the same representation. The stored A byte at 0x800E is 0x10; displayed group 17 has code 16. K4RJM supplied confirmed observations from physical-radio testing:

| Field | Radio address | Compact capture offset | Confirmed stored code |
| --- | --- | --- | --- |
| PTT ID delay | `0x900C` | `0x804C` | 28 = 3000 ms |

| VFO A MuteMode | `0x801B` | `0x801B` | 2 = QT/DQT + DTMF |

The decoder previously reduced these codes using `% 7`, `% 3` and `% 2`, respectively. It now preserves the full stored byte. The shared VFO squelch decoder also preserves VFO B byte `0x803B`. B has the same three existing options and its retained factory write frame stores code 2 directly; physical confirmation of B's behavior is still pending. This correction does not infer new signaling semantics.

The existing editor and write validator already support delay codes 0–28, PTT-ID codes 0–3 and squelch codes 0–2 for both VFOs. Their ranges and encoder are unchanged. Unknown codes remain visible as unrecognized saved values, survive DAT export, and are rejected by the existing write validator. They no longer become plausible defaults through modulo reduction. Other unrelated decoder normalization is outside this change.

### Factory CPS versus Bluetooth evidence

The maintainer observed that wired factory CPS displayed defaults for some F02 fields after reading the radio even though independent Bluetooth captures still retained the intended memory values. A later **factory write** changed the delay back to code 0. Those are separate events: a factory display/read conversion can lose a value before a later factory write changes memory. Do not attribute that sequence to this Bluetooth CPS, and do not classify it as a firmware defect without further evidence.

The retained `decoder-varied.img` contains squelch code 2 for both VFOs, while its native read DAT contains 0 for both. The optional fixture checker now permits exactly those two documented differences, keeping the historical native DAT intact. Its general-settings extraction also includes hand-transcribed rules; it is not an independent oracle for every setting.

A complete JSON diagnostic found in an unfinished-named download was preserved privately as a snapshot. Its `latestRead` timestamp is `2026-10-15T04:52:58.145Z`, build 20.10. The 33,344-byte capture contains decoded delay 0, PTT-ID 0, A squelch 0 and A combined byte `0x10`. This corroborates the later memory state and F03 byte, but cannot by itself prove the preceding sequence or the earlier high F02 codes. That earlier evidence is attributed to the maintainer's confirmed observations.

## F03 — remains open; encoder and decoder packing unchanged

The maintainer confirmed that official CPS wrote and read back **VFO A SignalCode 17 and FreqOffsetDir PLUS**, with radio byte `0x800E = 0x10`. The UI's group 17 is stored as zero-based code 16. Current A decoding returns group code 16 and direction 1 for that byte, consistent with that single observed configuration.

This does not identify a unique mapping. Current packing `(direction << 4) | group` maps all three configurations below to the same byte:

| Direction | Displayed group | Group code | Encoded byte |
| --- | --- | --- | --- |
| Off | 17 | 16 | `0x10` |
| Plus | 1 | 0 | `0x10` |
| Plus | 17 | 16 | `0x10` |

Across the full 3-direction × 20-group domain there are **60 inputs but only 52 distinct bytes per VFO**. Bytes `0x10`–`0x13` each have three possible inputs. The unchanged A decoder takes the entire byte as the group; B takes only the low four bits. Both extract direction starting at bit 4. Thus A Minus/group 1 becomes decoded group code 32, and B Plus/group 17 becomes decoded group code 0. The exhaustive round-trip test remains TODO because those mismatches are unresolved.

CHIRP is independent implementation evidence, not sufficient grounds to replace the mapping. The newly supplied `F03-GROUP17.dat`, `F03-PLUS.dat` and `F03-PLUS-GROUP17.dat` now independently establish the three distinct native inputs in the collision table. Relative to `MINI5_BLUETOOTH_FACTORY_RESAVED.dat`, they change only group, only direction, and both fields, respectively. **The current app reconstructs identical entire 33,344-byte images from all three DATs**, with SHA-256 `12467ed36d1f2751c19703cfc4c5dd0631a611d41c5b0c58680c4b97b98c7d35`. Thus the collision is reproduced with actual supplied factory inputs, not just constructed examples.

The supplied raw captures establish the combined Plus/group-17 byte `0x10`, including an exact whole-image match with the corresponding native DAT. They do not include isolated raw captures for Off/group 17 and Plus/group 1. Consequently, they do not establish how the radio distinguishes these inputs, or whether the factory write representation itself collapses them. No speculative shift/mask change, new combination restriction or firmware diagnosis is included. F03 remains open.

## Other findings established by the supplied files

### F01 — actual capture contains an unmapped byte lost by reconstruction

`MINI5_FACTORY_ORIGINAL_BT.dat` matches every field decoded from `mini5-diagnostic.json` (capture timestamp `2026-10-15T02:01:43.581Z`). Rebuilding that DAT produces exactly one difference among the 33,344 captured bytes: radio address **`0x9018`**, compact offset `0x8058`, changes from transport byte `0x42` to `0x00` (decoded value 1 to 0). This supplies a real captured example of F01 in addition to the original synthetic probes.

The purpose of this byte and the consequence of changing it remain unknown. This is an offline reconstruction result, not evidence that this application changed that byte on a physical radio. Later captures contain zero there, but their sequence does not establish which operation caused that change. No preservation rule or encoder change is justified solely by this observation. F01 remains open.

### F08 — native channel 999 confirmed; radio mapping still unverified

`F08-CHANNEL999.dat` contains a populated channel 999 (native record index 998), with the extra record 1000 empty. Its complete native-DAT semantic round trip passes. Relative to the factory-resaved baseline, only channel 999's RX frequency, busy lock, power and name differ; TX remains blank. The unchanged planner rejects it with the existing last-channel-pair guard. None of the supplied raw captures contains this populated channel 999, so the file does not establish its actual radio memory mapping. F08 remains open and the guard remains enforced.

### File pairing requires care

`F02-SAME-RADIO.dat` contains no occupied channels and has F02 codes 28/3/2 with direction Off/group 1. Its similarly named JSON contains 21 occupied channels and codes 0/0/0 with direction Plus/group 17. These are different configuration states and cannot be treated as a matching input/read-back pair. That JSON's raw memory is identical to `F03-AFTER.json`; `F03-SAME-RADIO.dat` is identical to `F03-COMBINED-TEST.dat`. These facts do not establish a failed write or its cause.
