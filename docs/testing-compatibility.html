HAM-RX BAOFENG MINI-5 · VERSION 20.27

Testing & Compatibility

Physical-radio evidence and software checks answer different questions. This record credits K4RJM's completed radio testing and identifies the limits that remain. Version 20.27 changes the interface, tutorials and documentation; Bluetooth protocols, memory mapping, encoding/decoding and programming behavior are unchanged.

Physical radio testing

K4RJM completed successful Bluetooth reads, programming, normal reboot, reconnection and readback on the recorded MINI-5 setup. The identified baseline is Radio 100, firmware V0.05, hardware V1.7. Typical programming took less than one minute in the reported tests.

Original factory CPS files and independent Bluetooth captures support the settings corrections and factory-compatible behavior. Build 20.14 before/after captures confirm the intended channel 71 addition and channel 999 clearing after reboot, with no changes outside those areas. Completed factory programming and captures also establish channel-999 capability. These results are physical evidence, not simulations.

See reboot/readback evidence, settings captures and channel-999 evidence. No physical-radio write was performed while developing this interface release. The results do not certify every MINI-5 firmware or hardware variant.

Verified software corrections

Settings decoding · 20.11
Retains evidenced values including PTT-ID delay code 28 (3000 ms), VFO PTT-ID code 3 (BOTH) and VFO A mute code 2 (QT/DQT + DTMF). F02 evidence.
Channel frequencies · 20.12–20.14
Corrects decoding and checks channel edits/programming against recorded factory ranges and the 1.25 kHz grid. Imported/read values remain preserved; unsupported channel frequencies block programming. VFO reception is separate. F07 evidence.
Radio identity · 20.18
Requires a complete fresh 5RMINI identity for the current connection before programming. Opening a DAT does not verify a radio; matching a model does not identify firmware. Identity policy.
Channel 999 · 20.20
Reproduces the factory trailing-memory pattern, matching all 33,344 captured bytes. Ordinary edits preserve channel 999; the reserved 1,000th DAT record remains uneditable. F08 evidence.
Stalled Bluetooth calls · 20.21
Deadlines stop stalled operations and late responses cannot resume cancelled work. A timed-out write remains uncertain and is never retried automatically. Deadline coverage.

Automated and browser testing

The complete Node regression suite has 155 passing tests. It covers native DAT preservation, independent captured-byte inputs, validation, write safeguards, asynchronous failures, cancellation, identity binding and channel boundaries. The separate browser suite has 21 checks covering actual DOM controls, editing, keyboard navigation, Undo, bulk movement, scrolling, pagination, fixed cell geometry, 23 hotspots, responsive Help, PDF viewing and programming protections.

Independent coverage means evidence that is not produced by the same encoder under test; it does not require another person to repeat K4RJM's testing.

Known limitations

  • VFO overlap: on tested VFO A, OFF/group 17, PLUS/group 1 and PLUS/group 17 can all read back as PLUS/group 17. This matches stock wired CPS. Exact firmware/configuration-format cause remains unconfirmed; it does not affect ordinary memory-channel records.
  • DAT scope: DATs contain CPS settings, not firmware or every raw-memory byte. Factory-compatible reconstruction can normalize unmapped areas. This does not prove that every such byte is unused.
  • Stock CPS defaults: wired CPS displayed defaults despite independent Bluetooth captures retaining intended values. A later factory write reset a delay to code 0. This separate observation is not automatically a Bluetooth-CPS or firmware defect.
  • Operating verification: matching readback bytes does not prove every on-air function. Confirm intended settings and radio operation.

All 15 original audit findings have final dispositions. F01 and F03 were accepted as factory-compatible limitations; closure does not mean the behavior has disappeared. Detailed limitations · Audit dispositions · Original audit.

Bluetooth reconnection concerns

The normal radio reboot after writing ends the connection. After all 262 write blocks are acknowledged, the app requests browser disconnect and waits for an explicit restart/reset confirmation before reconnecting and reading back. No fixed reboot timer or speculative radio reset command has been added.

Intermittent cases requiring Bluetooth to be toggled on both the PC and radio are not established as fixed. Completed successful reconnection tests and this intermittent concern can both be true. If a browser call remains pending, save your work and diagnostics, then wait or reload before reconnecting. An uncertain write must not be retried automatically.
